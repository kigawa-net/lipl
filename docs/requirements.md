# Lipl Requirements

> 関連ドキュメント: [README.md](../README.md) | [CLAUDE.md](../CLAUDE.md)

## Vision

飲食店向けの公式ページ作成サービス。

キャッチコピー:

お店の情報を入力するだけ。3分で公式ページを公開。

## MVP Flow

```
会員登録
  ↓
店舗作成（店名・業種・所在地）
  ↓
フォーム入力（営業時間・電話番号・SNSリンク・写真・メニュー）
  ↓
AIヒアリング（チャット形式でお店の魅力・こだわりを引き出す）
  ↓
LP生成（AIがテキスト・レイアウトを自動生成）
  ↓
プレビュー（スマホ・PCで確認）
  ↓
公開（<slug>-lipl.kigawa.net で即時公開）
```

### 所在地の入力形式（固定店舗・移動販売の対応）

- 業種（カフェ・居酒屋・ラーメン店・レストラン・キッチンカー等）とは別に、店舗作成時に **業態区分**（固定店舗 / 移動販売）を選択する。業態区分は業種選択と連動した既定値を持つ独立フィールドとして扱う:
  - 業種で「キッチンカー」を選んだ場合、業態区分は既定値として「移動販売」が自動設定される。他の業種を選んだ場合は「固定店舗」が既定値になる
  - 既定値はユーザーが変更できる（例: レストランを運営しつつ移動販売も行う店舗など、業種と実態が一致しないケースに対応する）
- **固定店舗**: 「所在地」は住所（必須）
- **移動販売**: 「所在地」の代わりに **出店エリア**（自由テキスト。例:「名古屋市内中心・出店スケジュールはSNSで確認」）を入力する（住所は必須としない）
- Pro の SEO 設定（LocalBusiness構造化データ等）は、**業態区分が「固定店舗」の場合のみ**出力する（業種の値ではなく業態区分の値で判定する。移動販売は住所が定まらないため対象外）

### フォーム入力項目の仕様

| フィールド | 必須 | 説明 |
|-----------|------|------|
| 店名 | ✓ | 最大50文字 |
| 業種 | ✓ | 事前定義リストから選択（カフェ・居酒屋・ラーメン店・レストラン・キッチンカー等） |
| 業態区分 | ✓（既定値あり） | 固定店舗 / 移動販売。業種選択と連動した既定値を持つ（詳細は上記「所在地の入力形式」参照） |
| 所在地（住所）／出店エリア | 業態区分により必須 | 最大200文字（入力形式は上記「所在地の入力形式」参照） |
| 営業時間 | — | 最大200文字（自由記述） |
| 電話番号 | — | 最大20文字 |
| SNSリンク | — | 事前定義リスト（Instagram・X・Facebook・LINE・TikTok・YouTube の6種）から選択し、プラットフォームごとに1件まで登録可（店舗全体で最大6件）。各URL最大500文字。リスト外のプラットフォームは対象外とする |

## 認証

- **Keycloak** を使用（`user.kigawa.net` で運用中のインスタンス）
- realm: `lipl`（新規作成）
- フロントエンドは OIDC (Authorization Code Flow + PKCE)
- バックエンドは JWT 検証（Keycloak の公開鍵で署名検証）
- パスワード管理・メール認証・パスワードリセットはすべて Keycloak に委譲
- **新規会員登録**: `lipl` realm でセルフサービス登録（Registration）を有効化する。ユーザーは `/login` からリダイレクトされた Keycloak のログイン画面上の「新規登録」リンクから自身でアカウントを作成する。Lipl アプリ側に独自の登録画面・登録APIは用意しない

## ネットワーク

- **店舗LPデフォルトドメイン**: `<slug>-lipl.kigawa.net`
  - slug は店舗作成時にユーザーが設定（英数字・ハイフンのみ）
  - **グローバル一意**（全ユーザー間で重複不可。先着順）
  - ワイルドカード DNS `*.lipl.kigawa.net` で一括解決
  - Ingress は slug をホスト名によりルーティング
  - **slug 変更時のリダイレクト**: 全プラン共通で旧 URL から新 URL へ **1年間** 301 リダイレクト（Free を含む。QRコード等の印刷物が旧URLを指している場合の失効を防ぐため）
- **独自ドメイン** (Pro): ユーザーが DNS を `lipl.kigawa.net` に CNAME → Ingress で `customDomain` をルーティング
  - **所有権確認**: 別途の確認フローは設けず、設定された CNAME が Ingress まで到達し cert-manager の HTTP-01 チャレンジ（CNAME経由でIngressが応答することのみを要求し、ユーザー側でDNSレコードを追加操作する必要がない）が成功したことをもって確認済みとみなす
  - チャレンジ未成功の間はダッシュボード上で「未検証」ステータスを表示し、独自ドメインでの公開は保留する
- **サービス自体**: `lipl.kigawa.net`（ダッシュボード・LP生成API等）

## AIヒアリングフロー

1. システムが店舗の基本情報（業種・所在地など）を読み込む
2. AIがオープンな質問をチャット形式で行う
   - 例: 「お店のこだわりを一言で表すと？」
   - 例: 「どんなお客様に来てほしいですか？」
   - 例: 「他のお店と違うと思うところは？」
3. 回答をもとにAIがLP用のキャッチコピー・説明文を生成
4. **質問数・生成回数の制限**

| プラン | AI質問回数 | LP生成回数 |
|--------|-----------|-----------|
| Free | 3回 | 1回 |
| Basic | 5回 | 月3回まで |
| Pro | 10回 | 月6回まで |

### 回数のリセット単位

- **AI質問回数**: LP生成・再生成を1回実行するたびに新しいAIヒアリングセッションが開始され、質問回数もそのセッション単位でリセットされる（セッションをまたいで積算しない）
- **AI生成回数（Free）**: **アカウント単位**で生涯1回のみの買い切り（店舗を削除して再作成しても引き継がれる。下記「上限の適用単位」の店舗単位ルールの唯一の例外）。再生成したい場合はBasic以上へのアップグレードが必要
- **LP生成回数（Basic/Pro）**: カレンダー月単位でリセット（毎月1日 0:00 にリセット）
- 「LP生成回数」は初回生成・再生成を区別せず合算してカウントする（Freeは生涯合計1回、Basic/Proは当月合計）

## お知らせ投稿仕様

- **対象**: Basic 以上
- **1件あたりの情報**: タイトル（最大50文字）・本文（最大1,000文字）・投稿日時
- **件数上限**: 上限なし
- **保持期間**: 削除するまで保持（自動削除なし）
- **公開 LP への表示**: 新しい順に最大5件を表示

## 予約リンク仕様

- **対象**: 全プラン
- **Free・Basic**: 1件（外部予約サービスのURLまたは電話番号リンクを1つ登録可）
- **Pro**: 複数件（プラットフォームごとに複数登録可。件数上限は実装時に決定）
- **表示**: 公開 LP 上に「予約する」ボタンとして表示する
- アクセス解析のリンククリック数計測対象（Pro のみ計測、下記「アクセス解析仕様」参照）

## 多言語対応仕様

- **対象**: Pro プランのみ
- **翻訳方式**: Claude API（Sonnet）による自動翻訳
- **対応言語**: 日本語・英語・中国語（簡体字）・韓国語
以下は、店舗が入力するすべてのテキスト項目（「フォーム入力項目の仕様」「メニュー仕様」「お知らせ投稿仕様」参照）を翻訳対象/対象外に**網羅的に**分類したものである:

- **翻訳対象**（Claude API で自動翻訳する自由記述文）: LP のキャッチコピー・説明文、メニューの品名・説明文、お知らせのタイトル・本文、出店エリア（移動販売の場合）、営業時間
- **翻訳対象外**（原文のまま表示する。固有名詞・定型値のため意訳・音訳や機械翻訳を行わない）:
  - 店名・所在地（住所）: 固有名詞であり、Claude翻訳でブランド名や住所表記が変わってしまうことを避ける（住所の番地・施設名等もローマ字化せずそのまま表示するのが一般的）
  - 業種・業態区分: 事前定義リストからの選択値。表示ラベルはアプリ側の言語別辞書（i18n）で翻訳する
  - 電話番号・SNSリンク・予約リンクのURL: 翻訳の必要がない値
  - メニュー価格・「税込」等の固定UI文言: 下記「メニュー価格の表示」参照
- **翻訳タイミング**: LP 生成時または手動で「翻訳を更新」を実行したとき
- **URL構成**: 言語ごとに独立したパスを付与する（`/`=日本語（既定）、`/en`、`/zh`、`/ko`）。SEO設定（hreflangタグ等）と両立させるため、クライアント側トグルのみで同一URLを共有する方式は採らない
- **言語切替 UI**: 公開 LP 上部に言語切替ボタンを表示し、各言語パスへのリンクとして機能する
- **メニュー価格の表示**: 価格の数値・通貨（円）はそのまま表示し、Claude による翻訳対象としない。「税込」等の固定UI文言はアプリ側の言語別辞書（i18n）で翻訳する（Claude翻訳の対象外）

## アクセス解析仕様

- **対象**: Basic 以上

### 計測項目

| 項目 | Basic | Pro |
|------|-------|-----|
| ページビュー数（日別） | ✓ | ✓ |
| ユニークビジター数（日別） | ✓ | ✓ |
| デバイス別（PC / スマホ / タブレット） | ✓ | ✓ |
| 流入元（直接 / 検索 / SNS / 参照元ドメイン） | — | ✓ |
| リンククリック数（電話・SNS・予約リンク） | — | ✓ |
| データ保持期間 | 90日 | 1年 |

### 計測方法

- フロントエンドからバックエンド API にアクセスイベントを送信
- 個人を特定しない集計データのみ保存（IPアドレスは保存しない）

### ダウングレードによる保持期間短縮時の扱い

- ダウングレードで保持期間が短縮される場合（例: Pro→Basicで1年→90日）、既存データを即時一括削除しない
- 保持期間の判定は日次バッチで行い、各データが**新プランの保持期間**を超えた時点で順次削除する（自然減。即時削除ではない）
- 再度 Pro へアップグレードした場合、削除されずに残っているデータはそのまま表示される（既に削除済みのデータは復元不可）

## 運用ルール

### 店舗数上限・複数店舗の運用

| プラン | 店舗数上限 |
|--------|-----------|
| Free | 1 |
| Basic | 3 |
| Pro | 10 |

- 複数店舗を持つ場合（Basic・Pro）、店舗一覧から1店舗を **メイン店舗** として指定できる（未指定時は作成日時が最も古い店舗をメイン店舗とみなす。安定運用中の店舗を既定にする趣旨）
  - ダウングレード時に維持する店舗の選定基準（下記「プラン変更」）は直近の利用実態を優先するため、意図的に**更新日時が新しい順**を用いる（メイン店舗の既定値選定とは目的が異なるため基準が異なる）
- **メイン店舗が削除された場合**、残っている店舗のうち作成日時が最も古い店舗を新たなメイン店舗として自動的に再指定する。店舗が0件になった場合は「メイン店舗なし」とし、次に店舗を作成した時点でその店舗をメイン店舗とする
- メイン店舗の用途はプラン変更時の挙動（下記「プラン変更」）で使用する
- **上限の適用単位**: 写真枚数・メニュー品数・AI質問回数・LP生成回数（Basic/Proの月次カウント）・お知らせ件数・アクセス解析等の各種上限は、いずれも **店舗単位** で適用される（店舗ごとに独立してカウントし、同一アカウント内の他店舗との合算・共有は行わない）
  - **例外**: FreeプランのAI生成回数（生涯1回）はアカウント単位でカウントする（店舗の削除・再作成をまたいで引き継ぐ。店舗単位にすると削除→再作成で無制限に生成し直せてしまうため）

### プラン変更（アップグレード・ダウングレード）

- ユーザーは `/dashboard/billing` の Stripe ポータルから、決済失敗とは無関係に**自発的に**プランを変更できる（アップグレード・ダウングレードいずれも対象）
- **ダウングレードにより新プランの店舗数上限を超える場合**、トリガー（自発的な変更／決済失敗による自動ダウングレード）を問わず同一ルールを適用する:
  - **メイン店舗を最優先**に、新プランの店舗数上限に達するまで残りの店舗を **更新日時が新しい順** で公開維持し、上限を超えた店舗は非公開になる（データは削除しない）
  - 例: Pro（上限10）で8店舗運用中に Basic（上限3）へダウングレードした場合、メイン店舗＋更新日時が新しい順の2店舗（計3店舗）が公開を維持し、残り5店舗は非公開になる
  - Stripe のプラン変更完了 Webhook と決済失敗による自動ダウングレードは、いずれも同じ処理にフックする
- アップグレード時、非公開になっていた店舗の公開状態は自動復元しない（店舗一覧から手動で再公開する）
- 再決済成功による復帰（下記「決済失敗・サブスクリプション停止」）のみ、全店舗の公開状態を自動復元する対象とする

#### Pro限定機能のダウングレード時の扱い

Pro からのダウングレード（Basic・Free いずれへも）で失われる質的機能は、データを削除せず以下のように無効化する:

- **独自ドメイン**: 独自ドメインでの公開を停止し、対応する cert-manager の Certificate リソースを削除する（証明書は失効）。ユーザー側の CNAME 設定はそのまま残るが、Ingress のルーティングを解除するためアクセス不能になる。`<slug>-lipl.kigawa.net` のデフォルトURLでの公開は継続する。再度 Pro へアップグレードした場合、保存済みの `customDomain` 設定を用いて再検証（HTTP-01 チャレンジ）のうえ再公開する
- **多言語対応**: 翻訳済みコンテンツは削除せず保持するが、`/en`・`/zh`・`/ko` 等の言語別パスは非公開になり 404 を返す（日本語版 `/` のみ公開を継続）。再度 Pro へアップグレードした場合、保持済みの翻訳データで即時に多言語パスを復元する
- **問い合わせフォーム・SEO設定・予約リンク複数**: 設定データは保持したまま、公開LP上での機能提供のみ停止する（再アップグレード時に即時復元）

#### Basic限定機能のダウングレード時の扱い（Basic・Pro → Free）

Basic 以上で提供される質的機能が Free へのダウングレードで失われる場合も、データを削除せず以下のように無効化する:

- **お知らせ投稿**: 既存の投稿データは削除しないが、公開LP上での表示・新規投稿の作成をいずれも停止する。再度 Basic 以上へアップグレードした場合、既存投稿はそのまま表示が復元される
- **アクセス解析**: ダウングレード後は新規のアクセスイベント記録を停止し、ダッシュボードのアクセス解析画面も非表示になる。既存の集計データは削除せず、保持期間ルール（上記「ダウングレードによる保持期間短縮時の扱い」）に従って自然減する。再度 Basic 以上へアップグレードした場合、記録を再開し、残っているデータは表示が復元される

### 店舗・LP の削除

- 店舗削除または LP 非公開設定を行った場合、**即時**に公開 URL が非公開になる
- 店舗削除時、その slug は**即時に解放**され他ユーザーが再利用可能になる（グローバル一意制約の対象から外れる）
- 店舗削除後に同一アカウントで新規店舗を作成しても、Free の生涯AI生成回数はアカウント単位でカウントされるため引き継がれ、リセットされない（上記「上限の適用単位」参照）

### 決済失敗・サブスクリプション停止

- Stripe から決済失敗の Webhook を受信後、**3日間の猶予期間**を設ける
- 猶予期間中は現プランを継続。3日後に Free へ自動ダウングレード
- ダウングレード時、Free の制限を超えるデータは非表示になるが削除はしない（店舗数超過時の挙動は上記「プラン変更」参照）
- 再決済が成功した場合は即時に元のプラン・元の公開状態（全店舗）へ復帰する
- **通知**: 以下の3タイミングでユーザーにメール通知を送信する
  1. 決済失敗を検知した時点
  2. 猶予期間終了の前日（ダウングレードのリマインド）
  3. ダウングレード実行時
- **猶予期間中の自発的プラン変更との優先順位**: 猶予期間中にユーザーが `/dashboard/billing` から自発的にプランを変更した場合、自発的な変更を優先し、決済失敗フラグと猶予期間タイマーは即時に解除する
  - 変更先プランへの決済が成功した場合（Stripeの支払い成功Webhook受信）: 即時に新プランへ移行する
  - Freeへの自発的な変更の場合（決済不要）: 即時にFreeへ移行する
  - どちらの場合も、3日後に予定されていた自動ダウングレード処理は実行しない（キャンセルする）
  - 猶予期間中に自発的な変更が行われなかった場合のみ、既定の猶予期間フロー（3日後にFreeへ自動ダウングレード）を適用する

### slug 変更

- 全プラン共通: 旧 URL から新 URL へ **1年間** 301 リダイレクト（Free を含む）
